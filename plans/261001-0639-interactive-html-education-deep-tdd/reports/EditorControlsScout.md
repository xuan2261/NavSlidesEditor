## 1. Format alignment and rotation

- **Current code:** `client/src/components/ribbon/ribbon-format-tab-element-position-size-rotation-controls.jsx:252-260` defines `rotateSelection`, applying a +90° rotation independently to each selected element. The Align buttons at `:352-381` instead call `onUpdateElement` with a single-element position: left sets `x: 0`, center sets `x` from the slide width and primary width, and right similarly uses the primary width. Thus, on multi-select, they do not align the selection as a group.
- **Existing selection-level API:** `useSlideOperations` exposes `alignElements` (covered by `client/src/hooks/use-slide-operations-align-group-distribute.deep.test.js`, which tests group left/right/center alignment and the fewer-than-two-elements case). The Format control receives `onUpdateElements`, not this API directly. Route its align action through the existing selection-level operation via the established caller/controller wiring, rather than applying the primary-element coordinate to every selected element.
- **Test to extend:** `client/src/components/ribbon/ribbon-format-tab-element-position-size-rotation-controls.test.jsx` currently pins single-element center alignment and slide-width-based center/right behavior. Replace or revise those expectations to cover group alignment through the Format control; retain the hook deep test for geometry behavior.
- **LOC:** Not verified; no line-count tool was available.
- **Risk:** Don’t conflate canvas/group alignment with slide-edge alignment. Existing hook tests describe group-relative bounds; confirm that is the intended semantics for these ribbon buttons before wiring them.

## 3. Selection update fanout and property ownership

- **Current logic:** `client/src/utils/element-update-fanout.js:20-34` defines `COMMON_KEYS` for shared geometry, lock/visibility, and fragment properties. `ownsProperty` at `:36-39` accepts type-specific updates only when the key is an own property of `ELEMENT_DEFAULTS[element.type]`. `SHADOW_KEYS` bypass that check at `:41-43`, except for `html` and `code`. `buildSelectionUpdates` applies these rules at `:77-105`.
- **Current coverage:** `client/src/utils/element-update-fanout.test.js` covers shadow fanout/exclusions, selected legacy optional image/code/markdown/chart fields, and rejection of a stale wrong-type `fontSize` at `:31-143`. Its factory assertions and `client/src/components/canvas/element-renderers/element-factory.smoke.test.js` exercise defaults/factory behavior. `client/src/data/element-defaults.test.js` guards the 19 canonical types, README count, typedef parity, auto-color defaults, and feature-coverage tracking.
- **Properties identified from the inspected panels/ribbon:**
  - **Image:** `longDescription` is written by `client/src/components/properties/image-properties.jsx:123-129`, but absent from image defaults; current fanout drops it for multi-selection. `alt`, citation fields, filter fields, border fields, `objectFit`, and `decorative` are present in image defaults. Image controls include `longDescription`, so default ownership would fix its fanout.
  - **Text font family/line height:** Canvas rendering consumes `fontFamily` and `lineHeight` (`client/src/components/canvas/canvas-element-wrapper.jsx:252-257`), while text defaults include neither. This scan did not establish which panel writes them; don’t treat renderer use alone as proof of a panel-originated update.
  - **Shadow:** `shadowX`, `shadowY`, `shadowBlur`, and `shadowColor` are explicitly handled as common-like special keys by fanout (`:41-43`); the tests verify supported types receive them and `html`/`code` do not.
  - **Shape text fields:** Shape defaults already include `text`, `fontSize`, and `textColor` (`client/src/data/element-defaults.js`, `shape` entry); the shape panel writes those fields at `client/src/components/properties/shape-properties.jsx:255-290`.
  - **Other inspected authored properties:** The chart, code, image, media, shape, table, timeline, misc, and ribbon control properties searched align with their respective defaults where checked. This is not an exhaustive audit of every dynamic update expression.
- **Recommendation:** Prefer adding genuinely supported persisted properties—such as image `longDescription`—to that type’s defaults, rather than broadening `COMMON_KEYS`. That preserves type-specific filtering for mixed selections. Before adding keys, check the defaults/README count guard and factory expectations; adding properties does **not** change the 19 element-type count, but may affect tests that assert the resulting defaults.
- **Test to extend:** Add a regression in `client/src/utils/element-update-fanout.test.js` proving `longDescription` fans to legacy image elements; if adding the default, extend the matching factory assertion there or in `element-factory.smoke.test.js`.
- **Risk:** Defaults also define which properties fan out to old persisted elements. Adding a default therefore changes selection-edit behavior, not just initial factory output. Avoid adding properties that are only renderer-internal or unsupported by a control.

## 4. Shape properties and rendering

- **Current controls:** `client/src/components/properties/shape-properties.jsx` already provides a label input at `:248-259` and, when text exists, size and color controls at `:262-294`; shape defaults include these properties. So those controls are not missing.
- **Renderer:** `client/src/components/canvas/element-renderers/shape-element-renderer.jsx` selects shape geometry from `element.shape` and renders SVG variants in `renderShape` (starting around `:54`); it renders rich `textHtml` or plain `text` around the end of the component, with `fontSize` and `textColor`. `ShapeRenderer` supports the listed shape kinds, but does not establish that shape kind is editable from Properties.
- **Shape-kind editing:** The Insert ribbon gallery in `client/src/components/ribbon/ribbon-insert-tab-element-galleries-panel.jsx:70-110` offers shape types when inserting; its selection callback at `:551-556` calls `onAddShape`. That is an insertion path, not an edit-selected-shape path. The inspected `shape-properties.jsx` has no shape-kind selector. A contextual gallery/control for changing the selected shape kind is therefore the clear gap.
- **Test to extend:** `client/src/components/properties/indeterminate-multi-select.test.jsx` covers ShapeProperties mixed-state behavior; extend with a selected shape-kind change test when adding the control. `client/src/components/canvas/element-renderers/auto-color-resolution.test.jsx` already renders ShapeRenderer geometries and can cover renderer compatibility if needed. `client/src/components/ribbon/ribbon-insert-tab-element-galleries-panel.test.jsx` covers insertion gallery previews, not editing.
- **Risk:** Preserve line-specific controls and avoid exposing shape-only kind changes for `line` elements. [INFERENCE] A shape-kind selector should reuse the existing gallery’s shape vocabulary/rendered previews to avoid divergent supported-type lists.

## 5. Multi-select mixed values

- **Selection controller:** The correct path is `client/src/hooks/editor-controller/use-editor-selection-controller.js`; it applies `buildSelectionUpdates` in `updateSelectedElements` around `:43-62`. It does not itself derive displayed control values.
- **Reusable helper:** `client/src/utils/selection-mixed-values.js:12-26` exports `computeMixedValues`, returning a primary value and `isMixed` per key. `client/src/components/properties/indeterminate-multi-select.test.jsx` already exercises mixed geometry, shared values, single selection, mixed shape fill/opacity, and write-through behavior. The Format ribbon also uses the helper (`ribbon-format-tab-element-position-size-rotation-controls.jsx:239-250`) to blank mixed geometry fields.
- **Defect implication:** Some Format controls still read from `selectedElement` directly: opacity’s slider uses its primary value at `:335-347`, and lock/action controls similarly use the primary element. Geometry already uses mixed placeholders through `numProps`; the format test suite covers mixed geometry behavior but does not currently establish mixed opacity UI behavior.
- **Proposed change and test:** Reuse `computeMixedValues` in the affected contextual control rather than adding a second indeterminate helper. Extend `client/src/components/ribbon/ribbon-format-tab-element-position-size-rotation-controls.test.jsx` for the exact control(s) confirmed to be incorrectly presenting a primary value; extend `indeterminate-multi-select.test.jsx` only if the corresponding Properties control is affected.
- **Risk:** Mixed indicators and edit semantics are separate: retain the existing `onUpdateElement` fanout path so editing a mixed control applies to the selected elements, without changing selection ordering or controller behavior.
