## Conventions and concrete risks
- Canonical game config is nested; `resolveGameConfig` supports flat legacy shape, and `createGameElement` emits canonical nested subtype configs (`game-element-types-constants.js:143-220`). Preserve nested updates and default clones.
- Project rule says files <200 LOC: `game-properties.jsx` is 519 LOC; split ContentTab/DisplayTab/editor logic into cohesive sub-200 LOC modules, preserving its public export and tests. Keep shared game logic under shared code per project guidance.
- Capability matrix, defaults, authoring UI, renderer reads and server room options currently disagree (notably Jeopardy, Four Corners, Relay, Trivia, Scattergories). Avoid assuming renderer consumption implies authorability.
- Jeopardy category questions and daily-double representation rely on `jeopardy-shared.js` helpers; avoid introducing a second question shape.
- Four-corners and relay both depend on parent-window globals, an undocumented bridge boundary and timer polling; standalone runtime will not supply it without an adapter.
- Trivia `rounds` defaults and preview imply editable rounds, but interactive is hardcoded round definitions and reads flat `element.questions`; schema/UI mismatch risks dead configured data.
- Hot-potato current question indexing, shuffleQuestions, showLeaderboard and allowLate defaults need deliberate mapping to existing server room APIs; current renderer ignores presentation state.
- Name picker weight is not a meaningful UI toggle without per-item weight representation and transport/server selection behavior.
- Reset/replay is inconsistent: local game phases/scores and server room state can diverge; define source of truth before adding reset controls.
