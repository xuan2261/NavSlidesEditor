## Finding 1: Phase 3 scale math preserves the default-size pt bug
- Severity: High
- Location: `phase-03-raw-pt-scale-propagation-in-shadows-borders-strokes.md` / Architecture + Step 1 (`scaleLength`), lines 58-84 and 121-129; plan-wide constraint in `plan.md` line 101.
- Flaw: Phase 3 says raw PPTX point lengths need canvas-px conversion, but proposed `scaleLength(value, scaleAxis)` only multiplies by source-to-canvas scale. For default 960x540 decks, `scale.x === 1` and `scale.y === 1`, so a 2pt stroke/shadow remains 2px instead of `2 * 4/3 = 2.7px`. The phase's own test `scaleLength(2, 4/3) => 2.7` only covers 4:3 scale and hides the default deck bug.
- Failure scenario: A normal 16:9 PPTX with 6pt shape shadow imports. Phase 3 lands green for 4:3 tests, but default 16:9 decks still render shadow/stroke/border 25% too small because all raw numeric pt fields are left at their pt value.
- Evidence: `normalizeSourceSize` computes `scale.x = CANVAS_SIZE.width / width` and `scale.y = CANVAS_SIZE.height / height`, so a 960x540 source produces scale 1 (`server/services/pptx-import/geometry.js:18-28`, `server/services/pptx-import/constants.js:10`). Current raw numeric fields are stored unchanged: shadows return `s.h`, `s.v`, `s.blur` (`server/services/pptx-import/mapper/utils-base.js:41-49`), image border width is raw (`server/services/pptx-import/mapper/map-image.js:35-36`), line stroke width is raw numeric (`server/services/pptx-import/mapper/map-shape.js:40-41`), diagram strokes are raw (`server/services/pptx-import/mapper/map-diagram.js:35-36`, `server/services/pptx-import/mapper/map-diagram.js:61-63`). Renderers consume those values as pixels/CSS units: client shape SVG uses `strokeWidth={sw}` (`client/src/components/canvas/element-renderers/shape-element-renderer.jsx:4-6`, `client/src/components/canvas/element-renderers/shape-element-renderer.jsx:24`), shared export emits box-shadow with `px` (`shared/src/element-renderers.js:80-84`).
- Suggested fix: Define one invariant for numeric PPTX lengths. If pptxtojson emits these in pt, `scaleLength` must multiply by `PT_TO_PX * scaleAxis`; if geometry scale intentionally replaces pt-to-px, remove the Phase 3 and plan-wide `pt -> px` claim. Add default 960x540 tests for borderWidth, strokeWidth, shadowX/Y/Blur, not only 4:3 tests.

## Finding 2: Phase 5 stores corrected table sizes but does not make renderers consume them
- Severity: High
- Location: `phase-05-table-fontsize-and-fontfamily-fidelity.md` / Requirements + Architecture + Step 3, lines 37-42, 63-67, 144-158.
- Flaw: The plan treats scaling `colWidths` and `rowHeights` in the mapper as enough for table visual fidelity. Current renderers ignore those arrays, so corrected values will sit in JSON without changing canvas, shared HTML export, or PPTX export layout.
- Failure scenario: A table with columns 100pt/200pt imports. Phase 5 changes stored `colWidths` to `[133,267]`, tests assert JSON, but the canvas still uses an even `table-layout: fixed` table. User sees equal-width columns, and visual fidelity remains wrong.
- Evidence: Mapper currently stores `colWidths` and `rowHeights` (`server/services/pptx-import/mapper/map-table.js:121-122`), and existing mapper tests only assert stored arrays (`server/services/pptx-import/mapper.test.js:856-877`, `server/services/pptx-import/property-mapping.test.js:177-195`). Client table renderer does not reference `colWidths` or `rowHeights`; it emits `<table style={{ width: '100%', height: '100%', borderCollapse: 'collapse', tableLayout: 'fixed' }}>` and per-cell styles only (`client/src/components/canvas/element-renderers/table-element-renderer.jsx:75-112`). Shared HTML renderer also ignores them and emits a full-size table (`shared/src/element-renderers.js:332-366`). PPTX export table path builds rows from `element.data` and never reads `colWidths` or `rowHeights` (`client/src/utils/export-pptx-basic-renderers.js:202-260`).
- Suggested fix: Add explicit renderer/export requirements: client uses `<colgroup>` or CSS grid widths and row heights; shared HTML renderer mirrors it; PPTX export maps widths/heights into table cell/options if pptxgen supports it or documents fallback. Add DOM bounding-box tests, not only JSON tests.

## Finding 3: Phase 6 targets the wrong shared shape rendering seam
- Severity: High
- Location: `phase-06-shape-rich-text-preservation-and-multi-run-metadata.md` / Architecture + Related Code Files + Step 3, lines 50-68 and 151-169.
- Flaw: The plan says update `shared/src/element-renderers.js` shape branch to honor `textHtml`, but the shared shape branch delegates all actual SVG/text output to `shapeSvgString(el)`. That helper only renders `el.text` as escaped SVG `<text>`, with no `textHtml` path. Changing only `renderShape` as sketched will not preserve rich text in shared present/export output unless `shapeUtils.js` is changed or an overlay is introduced.
- Failure scenario: Imported shape stores `textHtml` with bold/color spans. Phase 6 updates `shared/src/element-renderers.js` string test to contain `<b>`, but actual shared output still calls `shapeSvgString(el)` and only emits the plain `el.text`, so exported HTML/present mode loses rich formatting.
- Evidence: Shared renderer shape branch returns `${shapeSvgString(el)}` directly (`shared/src/element-renderers.js:148-150`). `shapeSvgString` only checks `if (el.text)` and emits SVG `<text>` with `escapePlainText(el.text)` (`shared/src/shapeUtils.js:99-106`), so `el.textHtml` is ignored. Mapper already stores both fields (`server/services/pptx-import/mapper/map-shape.js:48-61`).
- Suggested fix: Move the rich-text work to `shared/src/shapeUtils.js` or stop embedding shape text inside SVG and render an absolutely positioned sanitized HTML overlay. Tests must call `renderElement` or `shapeSvgString`, not a non-exported pseudocode `renderShape` helper.

## Finding 4: Phase 6 client `dangerouslySetInnerHTML` sketch is invalid for the current SVG shape renderer
- Severity: High
- Location: `phase-06-shape-rich-text-preservation-and-multi-run-metadata.md` / Step 3, lines 161-169.
- Flaw: The plan sketches rendering `element.textHtml` as a `<div dangerouslySetInnerHTML>` in the React shape renderer, but the current renderer places text inside an `<svg>` as a `<text>` child. A normal HTML `<div>` cannot be inserted as an SVG child. Without `foreignObject` or a separate absolutely positioned overlay, the implementation will either be invalid DOM or mispositioned.
- Failure scenario: Developer follows the plan literally and replaces the SVG `<text>` block with a `<div>`. Browser drops/relocates the node or renders it outside SVG coordinate rules. Rich text may appear in unit tests but not on the canvas at the correct shape center.
- Evidence: Client shape renderer returns `<svg ...>` and renders `element.text` through an SVG `<text>` element (`client/src/components/canvas/element-renderers/shape-element-renderer.jsx:103-125`). The generic canvas wrapper dispatches non-text elements to their registered renderer (`client/src/components/canvas/canvas-element-wrapper.jsx:127-174`), so there is no existing text overlay container around shapes. Client rich-text sanitizer exists and returns HTML (`client/src/utils/content-safety.js:20-46`), but the shape renderer has no `foreignObject`/overlay path.
- Suggested fix: Specify the rendering strategy: `foreignObject` inside SVG with sanitized HTML, or an absolutely positioned HTML layer above the SVG with flex centering and pointer-events behavior. Include canvas screenshot/DOM tests for centering, clipping, rotation, and selection handles.

## Finding 5: Phase 7 promotes shape padding but no shape renderer reads it
- Severity: Medium
- Location: `phase-07-text-insets-application-on-client.md` / Requirements + Client renderer, lines 36-40 and 90-102.
- Flaw: The phase says both text and shape mapped elements get top-level `padding`, but only plans a change in `canvas-element-wrapper.jsx` text content styles. Current shape text is rendered inside `shape-element-renderer.jsx`; wrapper padding for text elements will not affect shape labels or shared/export rendering.
- Failure scenario: PPTX shape has internal text inset. Mapper writes `padding` on the shape. Canvas still renders the label at exact SVG center with no inset, because `ShapeRenderer` ignores `element.padding`. Phase 7 success criteria pass for text boxes but shape insets remain broken.
- Evidence: Shape mapper currently stores `_pptxImportMeta.textInsets` but not a first-class padding field (`server/services/pptx-import/mapper/map-shape.js:61-63`). Canvas wrapper only handles `element.type === 'text'` inline with `textPreviewStyle` (`client/src/components/canvas/canvas-element-wrapper.jsx:86-87`, `client/src/components/canvas/canvas-element-wrapper.jsx:112-116`); shapes are delegated to `ShapeRenderer` (`client/src/components/canvas/canvas-element-wrapper.jsx:127-174`). `ShapeRenderer` renders shape text at center via SVG `<text>` and has no padding/inset logic (`client/src/components/canvas/element-renderers/shape-element-renderer.jsx:113-123`). Shared shape output also has no padding path (`shared/src/shapeUtils.js:99-106`).
- Suggested fix: Split Phase 7 into text-box padding and shape-text inset handling. For shapes, define how padding affects SVG text/HTML overlay and update both client and shared renderers. Add tests for shape insets separately from text elements.

## Finding 6: Phase 1 backward-compat conversion misses shared present/export rendering
- Severity: Medium
- Location: `phase-01-sanitizer-pt-to-px-conversion.md` / Step 4, lines 192-199; plan-wide backward-compat constraint in `plan.md` line 102.
- Flaw: Backward compatibility is framed as a client renderer fallback, but saved presentations are also rendered through shared HTML export/present paths. Those paths sanitize rich text via `shared/src/content-safety.js`, which currently strips unsafe scripts/URLs but does no CSS unit conversion. Old imported decks with `font-size: NNpt` will still inflate in exported/present HTML even if the canvas client fallback is added.
- Failure scenario: User opens an old imported deck and the editor canvas looks fixed after client fallback. They export/present HTML, and the same `font-size: 40pt` content renders as 53.3 CSS px because shared renderer never converted stored pt strings.
- Evidence: Shared text renderer emits `sanitizeRichTextHtml(el.content || '')` directly (`shared/src/element-renderers.js:104-108`). Shared sanitizer only removes scripts/event attributes and sanitizes URL attributes (`shared/src/content-safety.js:21-25`); it has no style parsing or pt-to-px conversion. Client text preview has its own sanitizer path (`client/src/components/canvas/canvas-element-wrapper.jsx:112-114`, `client/src/utils/content-safety.js:20-46`), separate from shared renderers.
- Suggested fix: Put the shared conversion in a module used by server import, client content sanitizer, and shared content sanitizer/renderText. Add a regression test that renders old `element.content` through `shared/src/element-renderers.js` and asserts no `pt` remains / computed font-size matches.
