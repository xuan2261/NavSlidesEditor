## Finding 1: Legacy non-960 imported decks remain broken after deploy
- Severity: High
- Location: `phase-02-resolution-mismatch-for-non-default-slide-sizes.md:245` Risk Assessment; `phase-02-resolution-mismatch-for-non-default-slide-sizes.md:230-232` Todo List
- Flaw: Plan identifies existing non-960 presentations need load-time clamp/migration, but implementation files only target new import/export paths. No loader/store migration is planned.
- Failure scenario: A user already imported a 4:3 deck before this fix. It is stored with `resolution: { width: 720, height: 540 }` while elements were scaled for 960-wide canvas. After deploy, opening that existing deck still renders on a 720-wide canvas, so content remains clipped/off-canvas. New imports improve, old saved work stays bad.
- Evidence: Current importer scales element boxes to `CANVAS_SIZE` via `normalizeSourceSize(...).scale` and `mapBox` (`server/services/pptx-import/geometry.js:18-28`, `server/services/pptx-import/geometry.js:31-40`), but stores source dimensions as presentation resolution (`server/services/pptx-import/mapper/map-presentation.js:140-168`). Client canvas trusts persisted resolution directly (`client/src/components/SlideCanvas.jsx:78-79`). `CANVAS_SIZE` is 960x540 (`server/services/pptx-import/constants.js:10`).
- Suggested fix: Add an explicit migration/load-normalization task for existing `_pptxMeta.originalSize` decks: if `_pptxMeta.originalSize` exists and `resolution !== CANVAS_SIZE`, rewrite/clamp `resolution` on load or migration, and add a regression test that loads a persisted legacy JSON deck.

## Finding 2: Phase 3 drops pt-to-px conversion for default-size strokes/shadows
- Severity: High
- Location: `phase-03-raw-pt-scale-propagation-in-shadows-borders-strokes.md:23-32` Overview; `phase-03-raw-pt-scale-propagation-in-shadows-borders-strokes.md:41-49` Requirements; `phase-03-raw-pt-scale-propagation-in-shadows-borders-strokes.md:66-72` Architecture
- Flaw: The phase states numeric stroke/shadow fields are raw PPTX `pt` and says `pt → px (x4/3)` is missing even when `scale.x = 1`, but the proposed `scaleLength` only multiplies by `scaleAxis`. For default 960x540 imports, `scale.x === 1`, so 2pt remains 2px instead of 2.7px under the plan's own unit-conversion model.
- Failure scenario: A default-size deck with 3pt image borders, line strokes, or shadows imports with correct element bounds but undersized stroke/shadow widths. Corpus can pass geometry while the visual result remains thinner than PowerPoint.
- Evidence: Current raw fields are stored without conversion: shadows return `s.h`, `s.v`, `s.blur` unchanged (`server/services/pptx-import/mapper/utils-base.js:41-49`), image border width is raw (`server/services/pptx-import/mapper/map-image.js:35-36`), line stroke width is raw numeric (`server/services/pptx-import/mapper/map-shape.js:40-41`), diagram strokes are raw (`server/services/pptx-import/mapper/map-diagram.js:35-36`, `server/services/pptx-import/mapper/map-diagram.js:61-63`). Renderers interpret these as pixel/CSS values: shared `box-shadow` uses `px` (`shared/src/element-renderers.js:80-84`), client shape SVG uses `strokeWidth={sw}` (`client/src/components/canvas/element-renderers/shape-element-renderer.jsx:4-6`, `client/src/components/canvas/element-renderers/shape-element-renderer.jsx:24`).
- Suggested fix: Decide the invariant once. If these are PPT point lengths, `scaleLength` must multiply by `PT_TO_PX * scaleAxis`; if geometry scale intentionally replaces pt-to-px, remove the Phase 3 claim that default-size decks need x4/3 and update acceptance criteria accordingly. Add default-size tests, not only 4:3 tests.

## Finding 3: Table width/height fields are stored but not rendered
- Severity: High
- Location: `phase-05-table-fontsize-and-fontfamily-fidelity.md:36-38` Requirements; `phase-05-table-fontsize-and-fontfamily-fidelity.md:63-68` Architecture; `phase-05-table-fontsize-and-fontfamily-fidelity.md:72-78` Related Code Files
- Flaw: Plan scales `colWidths` and `rowHeights`, but does not require canvas/shared/export table renderers to consume those arrays. Storing corrected arrays alone does not affect visual fidelity.
- Failure scenario: Import a table with non-uniform columns. The mapper stores scaled widths, but editor/export still renders equal columns because no `<colgroup>`, grid template, or row height style uses the arrays. The bug survives while mapper tests pass.
- Evidence: Mapper currently stores `colWidths`/`rowHeights` (`server/services/pptx-import/mapper/map-table.js:121-122`), and tests only assert stored values (`server/services/pptx-import/mapper.test.js:856-877`, `server/services/pptx-import/property-mapping.test.js:177-195`). Client table renderer renders a normal `<table>` with cell styles but no `colWidths`/`rowHeights` usage (`client/src/components/canvas/element-renderers/table-element-renderer.jsx:80-112`). Shared renderer likewise emits `width:100%;height:100%;border-collapse:collapse` without col/row sizing (`shared/src/element-renderers.js:332-366`).
- Suggested fix: Add renderer/export requirements and tests: use `<colgroup>` or CSS grid/table-layout with `colWidths`, apply row heights, and assert DOM cell bounding boxes. Include client canvas, shared HTML export, and PPTX export paths.

## Finding 4: New table font fields are not preserved through edit/export paths
- Severity: High
- Location: `phase-05-table-fontsize-and-fontfamily-fidelity.md:36` Requirements; `phase-05-table-fontsize-and-fontfamily-fidelity.md:72-83` Related Code Files; `phase-05-table-fontsize-and-fontfamily-fidelity.md:188-194` Risk Assessment
- Flaw: Plan adds `cellStyles.fontSizes`/`fontFamilies` but does not cover existing table edit operations and PPTX export cell rendering. This creates silent data drift: styles may render initially, then disappear or attach to wrong cells after row/column edits or export.
- Failure scenario: User imports a styled table, adds/removes a row/column, then exports. `data` shape changes but new style arrays are not resized/truncated. A font from a deleted column can apply to a later cell, or export ignores per-cell fonts entirely.
- Evidence: Table add/remove buttons only update `data` and do not touch any `cellStyles` arrays (`client/src/components/properties/table-properties.jsx:29-47`). Current defaults list `cellStyles` without font sizes/families (`client/src/data/element-defaults.js:134-146`). PPTX table export reads `cellStyles` but only exports bg/text color, bold, align, vAlign, and uses global `element.fontSize` (`client/src/utils/export-pptx-basic-renderers.js:219-250`), so per-cell font size/family would not round-trip.
- Suggested fix: Extend Phase 5 to update table edit operations and PPTX export. Add tests for add/remove row/col preserving/truncating all `cellStyles.*` matrices and export tests asserting per-cell `fontSize`/`fontFace`.

## Finding 5: Shape `textHtml` render plan conflicts with current SVG renderer
- Severity: High
- Location: `phase-06-shape-rich-text-preservation-and-multi-run-metadata.md:35-42` Requirements; `phase-06-shape-rich-text-preservation-and-multi-run-metadata.md:151-169` Step 3
- Flaw: Plan says client shape renderer should render `textHtml` with a normal `<div dangerouslySetInnerHTML>`, but current shape renderer draws text inside an SVG `<text>` node. Dropping an HTML `<div>` into that SVG tree is invalid unless wrapped in `<foreignObject>` or rendered as an absolutely positioned overlay.
- Failure scenario: A shape with rich text imports with `textHtml`, but the canvas renderer either ignores it, produces invalid DOM, or overlays text outside the shape coordinate system. Unit tests that only assert string presence in shared renderer won't catch canvas misplacement.
- Evidence: Mapper already stores both plain `text` and `textHtml` (`server/services/pptx-import/mapper/map-shape.js:48-61`). Client renderer currently renders shape text only through SVG `<text>` and `{element.text}` (`client/src/components/canvas/element-renderers/shape-element-renderer.jsx:103-125`); it has no HTML overlay/foreignObject path. Shared renderText sanitizes rich HTML for text elements (`shared/src/element-renderers.js:104-108`), but shape rendering is a different renderer branch.
- Suggested fix: Specify exact rendering strategy: either SVG `<foreignObject>` with sanitized HTML and sizing, or an absolutely positioned HTML overlay above the SVG. Add Playwright/DOM tests that verify rich shape text is visible, clipped inside the shape bounds, and preserved in exported HTML/PPTX.

## Finding 6: Phase 8 visual import spec uses the wrong endpoint and wrong response contract
- Severity: Critical
- Location: `phase-08-acceptance-gate-corpus-visual-regression-and-rollout.md:98-120` Visual regression spec
- Flaw: Sample visual spec posts to `/api/pptx-import` and expects `{ id }` in the response. The actual route is `/api/pptx/import`, returns `202 { jobId }`, and requires polling `/api/pptx/jobs/:jobId` before a presentation exists. The planned acceptance gate can fail before testing fidelity or be implemented against a fake contract.
- Failure scenario: Team implements the spec from the plan. CI either gets 404/405 on `/api/pptx-import`, or destructures `id` from a 202 job response and navigates to a non-existent editor route. Visual gate never validates rendered import fidelity.
- Evidence: Actual router mounts `POST /import` under `/api/pptx` (`server/index.js:115-116`, `server/routes/pptx-import.js:87-102`). Existing e2e helper posts to `/api/pptx/import`, polls `/api/pptx/jobs/${jobId}`, then updates a presentation (`tests/e2e/pptx-import-fidelity.spec.js:13-26`, `tests/e2e/pptx-import-fidelity.spec.js:36-52`). Roundtrip e2e uses the same contract (`tests/e2e/export/pptx-import-endpoint-roundtrip-across-multiple-fixtures.spec.js:27-39`).
- Suggested fix: Replace the Phase 8 pseudocode with the existing async helper flow: POST `/api/pptx/import`, poll job until `done`, `apiUpdatePresentation`, then navigate to `/editor/:id`.

## Finding 7: Acceptance criteria cannot prove source font-size fidelity
- Severity: High
- Location: `plan.md:88-92` Acceptance Gate; `phase-08-acceptance-gate-corpus-visual-regression-and-rollout.md:37-42` Requirements; `phase-08-acceptance-gate-corpus-visual-regression-and-rollout.md:73-95` Acceptance criteria module
- Flaw: The plan requires rendered DOM font-size to equal original PPTX font-size, but the proposed assertion API takes `sourcePtFontSize` as an external parameter and the phase does not specify how to bind source runs to imported DOM elements/runs. Existing corpus scoring is semantic/category-level and will not catch per-run font drift.
- Failure scenario: Importer converts some text runs correctly and others incorrectly. Acceptance passes because it only sees element-level `fontSize` or synthetic tests, while actual DOM spans from `element.content` still contain wrong units or wrong dominant-run metadata.
- Evidence: Current corpus fidelity scorer matches elements and scores broad capture categories (`server/services/pptx-import/pptx-import-semantic-and-roundtrip-fidelity-tester.js:199-256`); table scoring only checks data/styles existence, not exact font metrics (`server/services/pptx-import/pptx-import-semantic-and-roundtrip-fidelity-tester.js:655-672`). Existing e2e fidelity checks element bounds and persistence, not computed font sizes (`tests/e2e/pptx-import-fidelity.spec.js:61-91`). Text rendering source is sanitized HTML `element.content` in the client (`client/src/components/canvas/canvas-element-wrapper.jsx:112-114`), while mapper metadata extraction currently summarizes runs separately (`server/services/pptx-import/mapper/utils-text.js:47-68`).
- Suggested fix: Add a source-to-DOM trace artifact per corpus deck: parse pptxtojson runs, assign stable element/run indices, store expected font/letter spacing in test metadata, then in Playwright inspect actual rendered spans by imported element id. Synthetic assertion tests alone are not enough.

## Finding 8: Rollback plan ignores PPTX export aspect-ratio regression
- Severity: Medium
- Location: `phase-08-acceptance-gate-corpus-visual-regression-and-rollout.md:240-242` Rollback plan; `phase-02-resolution-mismatch-for-non-default-slide-sizes.md:143-178` Round-trip patch
- Flaw: Rollback note says new imports with `resolution: 960x540` are safe because old code reads that as-is. That is only true for canvas rendering. Old exporter derives slide layout from `presentation.resolution`, so a post-fix 4:3 import exported after rollback becomes 16:9 and loses original aspect ratio.
- Failure scenario: Deploy fix, users import 4:3 decks, then rollback due import failures. Canvas opens, but exporting those decks on rolled-back code produces 16:9 PPTX. This is a data/roundtrip regression across rollback.
- Evidence: Server export currently uses `getPresentationResolution(presentation)` then `getPptxLayout(resolution)` for PPTX layout (`server/utils/server-export.js:24-29`). Shared helper reads `presentation.resolution` only (`shared/src/shared-pptx-core.js:13-19`). Client export has the same pattern (`client/src/utils/exportPptx.js:69-75`, `client/src/utils/export-pptx-core.js:13-22`). Phase 2 itself acknowledges this would destroy 4:3 round-trip after changing resolution to 960 (`phase-02-resolution-mismatch-for-non-default-slide-sizes.md:143-154`).
- Suggested fix: Rollback plan must include a compatibility patch or feature flag that teaches old/export code to prefer `_pptxMeta.originalSize` for layout before changing import storage. At minimum, document export-aspect rollback risk and add a rollback rehearsal test.
