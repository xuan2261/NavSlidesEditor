# Phase 1 OfficeCLI physical feasibility blocker

Observed on 2026-09-25 on Windows 10 x64, before G0. This is a failed physical spike, not a qualification receipt.

- The default `officecli.exe` found through PATH reports `1.0.152`, length `33,460,136`, SHA-256 `047705402974C3690A4437E55F620D03AFAC4BEBA4FDD28FDB59AF610A3AFFF2`. It is not the pinned candidate and was not passed to the physical runner.
- A separate locally installed `1.0.135` candidate reports the required `33,111,928` bytes and SHA-256 `937DB176B585E874AA5BFF48D536BCE78037665CD862B5DEEFE56E79977E6588`. The official [v1.0.135 release](https://github.com/iOfficeAI/OfficeCLI/releases/tag/v1.0.135) points to commit `d2d9c60f44537004c3e1f46680c24ea38d9659c2`; its [SHA256SUMS](https://github.com/iOfficeAI/OfficeCLI/releases/download/v1.0.135/SHA256SUMS) lists this executable hash. The upstream [LICENSE](https://raw.githubusercontent.com/iOfficeAI/OfficeCLI/v1.0.135/LICENSE) is Apache-2.0, SHA-256 `7E282402A5A6DB33995FE638BB3FE79013F9884D8F7D15A42E481C1E86AADDA1`. Upstream [NOTICE](https://raw.githubusercontent.com/iOfficeAI/OfficeCLI/v1.0.135/NOTICE) exists. NavSlides does not bundle this optional executable.
- First real invocation of `node scripts/officecli/run-physical-feasibility.mjs` with all three pinned fixtures failed with `LEGAL_PROVENANCE_UNRESOLVED` before the manifest's legal and provenance fields were reviewed. The manifest was updated using the upstream sources above.
- Second real invocation with the matching local candidate and a timestamp taken from that file's local creation metadata failed with `PROCESS_FAILED: OfficeCLI validation failed`. The runner did not create `officecli-physical-feasibility.json`.
- Direct invocation of that same executable with `validate server/data/test-corpus/adversarial/good-package.pptx --json` returned exit code 1 and `success: false`. Its structured warnings report two package errors. `[Content_Types].xml` lacks a default `rels` content type and the package lacks the required office-document relationship. The fixture passes NavSlides' safety preflight but does not pass the real OfficeCLI OPC validator. No slide content, process raw output, or local path is retained here.
- To test the fixture hypothesis, local PowerPoint COM `16.0` produced a disposable one-slide `.pptx` outside the repository. The same pinned OfficeCLI returned exit code 0 and `success: true` for it. This proves a valid PowerPoint-generated fixture is feasible, but it is not the pinned checked-in fixture, was not passed through the production gateway, and is not release evidence.
- The production `parseValidationResult` requires `valid: true`, but actual `1.0.135` JSON on that successful disposable package has `success: true` and no `valid` field. Passing real stdout from exit code 0 to the production decoder failed with `OfficeCLI validation output does not report success`. Existing unit doubles report `valid: true` and conceal this schema mismatch. This is an independent Phase 1 stop condition, even after replacing the invalid fixture.
- [Phase 8 G1](../phase-08-direct-officecli-qualification-g1.md) additionally requires an isolated, non-administrator clean Windows account or VM with denied egress and no project secrets. These invocations ran in the ordinary developer session and do not satisfy that isolation prerequisite. Phase 1's smoke recipe needs an explicit isolation profile and matching receipt before G1 can consume its evidence.
- Independent receipt review found that `assertAuthoritativeReceipt` can accept three copies of the positive fixture because it checks count and membership, not distinct coverage. The physical runner's top-level error handler can also print local absolute paths from filesystem errors. Fix both before accepting a receipt. No positive receipt exists to test against today.
- The matching local executable's creation time is not independent evidence of administrator acquisition. The failed run carried this metadata as `acquiredAt`, but produced no receipt. Obtain a verified acquisition record before a future claim.

The Phase 1 stop rule applies. Do not approve the pre-G0 gate, start G0, or treat the unit-test doubles as physical evidence. Re-plan the valid-fixture contract explicitly, then pin and exercise a genuinely OfficeCLI-valid PowerPoint package through the existing gateway. A replacement fixture changes the pinned fixture hashes and the expected receipt; it needs reviewed provenance and a failing-before regression check. Phase 2 and later phases remain dependency-blocked until this gate is resolved. No full-suite or release-success claim was made.
